# Context
See proposal.md. PostgreSQL owns tasks, runs, leases, attempts, schedules, effects and memory revisions; Graphile wakes workers; Pi restores checkpoints. Operational completion is currently narrower than verified external completion.

# Goals / Non-Goals
Keep the existing execution path and optional providers. Do not promise exactly-once remote delivery or rely on mobile background execution. Do not add a vector store or save private tool transcripts indiscriminately.

# Decisions
- Extend existing records and shared contracts additively; do not create a parallel task runner. Preserve old-client status behavior through a projection.
- Verification is deterministic destination evidence for structured effects, not prose keyword scoring. Ambiguous commits are reconciled before replay, with stable semantic keys.
- Auth failures require intervention; transient failures use bounded exponential delay with jitter and dependency-scoped circuit state in Postgres. No process-local global resource bottleneck.
- Workflow permissions are enforced at the execution boundary, not merely prompts. Mail never permanently deletes; calendar and subscription checks do not modify external records.
- Existing health tooling supervises services independently of Pi with bounded restart cooldown and escalation.
- Deterministic proactive triggers precede model judging regardless of configured discretionary stage order.

# Risks / Trade-offs
- Unknown remote commit → preserve uncertainty and reconcile destination before retry.
- Old clients and rolling deployments → nullable additive fields and compatible status projection.
- Historical completions lack evidence → mark unknown, never fabricate verification.
- Sensitive evidence → store identifiers and minimal structured results, redact diagnostics.

# Effect classification and destination obligations

The completion guard currently counts every `failed` effect as unresolved. `completeExternalEffect` uses that status for explicit tool errors, but the status does not distinguish a request rejected before dispatch, a definitive failed action, or an external action that may have partially executed. An otherwise handled validation or stale-revision error therefore fails the whole run. A focused run of the existing executor approval and self-settings tests found six failures of this kind (shared-memory validation and revision conflicts, stale approved instructions, offline desktop, and invalid desktop actions). This is a release blocker, not evidence that approval enforcement should be weakened.

Represent pre-dispatch rejection, definitive failure and ambiguous/possibly partial dispatch as distinct durable outcomes. Preserve the authenticated/trusted approval path, the effect's audit history, replay semantics, lease fencing and its original result; do not convert a failed action into a successful effect or issue it again just to clear the guard. Existing `failed` rows lack this classification and must remain conservative until independently reconciled. Moving checks before the gate alone is insufficient because it changes effect and audit records and can alter approval replay. Device disconnects and exceptions after dispatch cannot be classified as no-effect without an authoritative receipt.

Persist a structured task or workflow destination obligation and evidence tying a verified outcome to the correct intended destination and action. A known no-effect rejection may be reported as a failed or declined action and, where the user explicitly changes the goal or a subsequent verified action satisfies the same obligation, resolved without claiming that the rejected action succeeded. `uncertain` and live `executing` effects remain unresolved until safely reconciled. A successful source read, an unrelated later effect, a saved configuration, or a natural-language assertion does not satisfy a destination write obligation. Define how a user-visible response reports a known failure without assigning unsupported task success; do not use prose keyword matching to infer success. Cover approval replay, concurrent claims, old rows, pre-dispatch rejection, partial writes, explicit failure, uncertain outcomes, retries to the same or a different destination, and real verified destination success before relaxing the guard.

A safe implementation needs an internal-only completion operation at the call boundary, invoked exclusively at individually reviewed branches that demonstrably occur before any side-effect dispatch. Persist the new no-dispatch classification, the original failure result and the existing approval/audit metadata together under the current run lease and effect status compare-and-set; a stale worker must not reclassify an effect after another attempt has taken ownership. A connector response, arbitrary result fields, free-form error text, thrown exception after dispatch, or model assertion cannot choose this classification. The existing status is stored as text, but adding an outcome still requires checking all readers, rolling-version behavior and projections; it must not reinterpret historical `failed` rows. Duplicate approval replay must return the recorded rejection rather than re-execute or silently drop approval history.

The completion guard may distinguish a proven no-dispatch failure from an ambiguous write, but that distinction alone does not fulfill the user's requested destination action. A required obligation remains unsuccessful until the owner changes it or independently verified evidence satisfies that same obligation; optional diagnostics must be identified by trusted structured workflow state, not guessed from tool names or result text. Add tests that attempt to spoof internal classification through connector output, race a stale lease against recovery, replay a prior approval, read legacy `failed` rows, and compare a verified retry to the same obligation with an unrelated success. Until this shared classification and obligation plumbing exists, continue to fail closed rather than exclude the failures solely by status.

# Routine notification evidence and recovery gap
The current routine-completion path finalizes the run before it invokes the notification provider. A crash in that interval leaves no durable completion-notification intent to recover. The generic notification `send` contract returns no delivery outcome, while the Expo adapter's `send` drops the `undeliverable` result; accepted push tickets and receipt checks do not by themselves establish that the owner saw a notification. The existing exhausted-retry notice reconciler is at-least-once and explicitly allows replay after a crash. The previously deployed Expo transport retries after a network failure or an interrupted response read, so a provider acceptance followed by a lost response can produce a duplicate. A focused test reproduced the second request; it did not establish whether Expo accepted the first request. A local, undeployed transport change stops automatic request-level retries after an ambiguous send, marks those results uncertain and rejects success-shaped responses without an acceptance ticket. It does not stop higher-level callers from replaying, persist outcomes, or close the finalization-to-notification crash window.

The missed reminder's actual cause remains unknown. Its run completed and later chat history was cleared, removing the associated message/event evidence. A current push registration and session covering the scheduled time do not establish provider acceptance or device display. Do not infer a historical delivery outcome from these observations.

Implement the durable notification requirement in the existing execution and job infrastructure. Commit a unique intent with the final run/message transaction, recover it through fenced claims, and keep notification state separate from execution completion. Store references to already protected message content, not plaintext copies, and define retention/clear behavior and authorization before implementation. Submit only once where the provider cannot safely deduplicate; an interrupted or ambiguous submission requires an explicit uncertain outcome and reconciliation or owner intervention, not blind replay. Treat definitively unsubmitted work separately from ambiguous requests. Record ticket acceptance and subsequent receipt as distinct facts, with no claim of device display. Exercise the crash boundaries, conflicting workers, tenant isolation, preference changes and ambiguous provider responses in automated tests, then verify the actual authenticated notification path before any release claim.

## Durable routine schedule and wake-up ordering

Status: design requirements only; not implemented or validated for release. The schedule row and the Graphile job are currently written in separate operations. Because all wakes for one routine share `routine:<id>`, a delayed earlier enqueue can replace a newer schedule, and a delayed cancel can remove the newer job. The existing reconciler scans schedules within a one-minute lookahead every 30 seconds and may repair the result, but that is eventual recovery, not atomic publication. The deterministic offline reproducer `work/routine-scheduler-race.mts` in the projectless task workspace uses the actual in-memory job queue and reproduces the old publication replacing the newer keyed job. This is not production or PostgreSQL concurrency evidence.

Do not switch to keys derived only from routine ID and timestamp. A pause and later rearm can use the same timestamp, so an old cancellation can remove the new job; long-future stale publications can also remain queued without bound. Nor is a read-before-enqueue or row-locked queue synchronization alone an atomic commit of the routine change and its wake: a process can die between the two commits. Routine `updatedAt` is not a schedule generation because unrelated edits change it.

A releaseable design requires an explicit monotonic schedule generation, advanced in the same transaction as each schedule mutation or claim, and a durable queue or outbox intent committed in that transaction. The generation must cover create, update and rearm, worker claim and advance, watch retry/pause/advance, account backoff, bot archive/destroy, routine deletion and reconciliation. It must be checked in the worker's atomic claim, not merely before it, and in any publisher/cancellation decision. Stale work and stale cancellation must never mutate or remove the current generation, including an ABA pause/rearm for the same time. A single replace key can stay bounded if every add/remove is fenced against the current locked row and committed atomically with the matching state transition; otherwise a separately bounded generation-aware outbox and cleanup is needed. Preserve no-early-run behavior and existing at-most-once routine claim semantics.

Graphile's `add_job` and `remove_job` are database functions, but direct use from a Prisma transaction must first be shown to work with the runtime role, RLS context, lock order, payload wrapping, retry behavior, and Graphile's handling of locked jobs. Graphile is initialized separately from application migrations, and the `memory` wakeup driver is also supported, so a migration that unconditionally calls Graphile or silently drops the in-memory path is not acceptable. For deletes and bot destruction, capture and invalidate outstanding work within the same durable transaction; the existing destroy path cancels before the bot deletion transaction. Establish the worker schema and permissions before requiring it, specify fallback/recovery when it is unavailable, and preserve approved rollback behavior. A live rollout must drain old API and worker code that does not honor the new fence; schema backward compatibility alone is not evidence.

Required evidence: deterministic interleavings of old/new publish and cancel in both orders; same-time rearm; duplicate and locked jobs; worker claim racing pause, archive and delete; transaction rollback, crash before/after commit and recovery; bounded stale-job cleanup and retention; Graphile permissions/RLS and current installed schema; mixed-version rollout and rollback; and the memory-driver contract. Run real isolated PostgreSQL/Graphile tests in addition to deterministic unit tests, without production data, before claiming the scheduler race closed.

### Remaining implementation boundary

A publisher that holds a routine/outbox transaction open and then calls the existing `JobPublisher` is unsafe with the current pool-sharing architecture. The worker passes the same bounded `pg.Pool` to Prisma and `GraphileJobPublisher`; if all connections are held by such transactions, every nested queue publication waits for a connection that cannot be released. The offline `work/routine-pool-contention.mts` harness reproduces this with the real `pg-pool` and fake clients (two held connections and two waiting nested publishers); it is a pool-contention demonstration, not a database or production run. A transaction-aware publisher using the transaction's own connection would need a non-Graphile equivalent and explicit failure semantics; acquiring a second pool without a deployment-approved resource design is not a solution.

An application-only generation increment also fails the repository's documented old/new overlap: an old API or worker can write a schedule without advancing the new generation. A database trigger could cover old writers, but must not be introduced as an assumed solution. Until a supported cross-driver atomic publication or durable-outbox contract and mixed-version compatibility are verified, retain task 2.6 as a release blocker; no scheduler schema, migration or production behavior has been changed by this investigation.

### Isolated protocol prototype and rollout prerequisites

In the existing isolated PostgreSQL 16 fixture, a separate synthetic schema prototyped a schedule-change trigger that increments a generation and upserts a durable outbox row in the same transaction. In that prototype, rollback retained the original schedule and outbox, a same-time pause/rearm incremented the generation, deletion persisted a tombstone, and two concurrent transactions serialized to matching final generation and outbox state. A separate test switched on a protocol gate and observed an old-shaped writer rejected while a new-shaped writer succeeded. This is an experiment using synthetic tables and a role-specific session marker, not the production schema, provider, migration, or an authorization mechanism. The marker is settable by a database client and must not be treated as a security boundary. Fixture scripts are `work/scheduler-protocol-fixture.sql`, `work/scheduler-protocol-check.sql`, and `work/scheduler-protocol-concurrency.mts` in the task workspace; the concurrency check used two bounded fixture connections.

Before enabling a real implementation, define and test a cutover that drains or blocks legacy job acquisition and **pre-claim** work across every old API and worker. A write trigger alone is insufficient: an old routine worker can perform watch checks, including command watches, before it attempts the fenced row update. A legacy publisher can also enqueue or cancel a generation-unaware job without touching the routine row. The new protocol needs generation-aware job payloads and keys isolated from the legacy namespace, an atomic generation check at claim, and a tested bounded cleanup strategy that handles late publishers and locked jobs. Reconciliation of a durable intent must not hold a database connection while requesting another from the same saturated pool. Prove PostgreSQL/Graphile installation, permissions, RLS, job wrapping and cancellation behavior, memory-driver publication, bot archive/delete and rollback semantics before activation. During a rolling upgrade, legacy instances must not perform the protected paths after the cutover, and rollback must explicitly restore or reconcile pending schedules. The isolated trigger demonstration does not satisfy those release gates.

An additional disabled-by-default migration candidate is saved only as `work/scheduler-foundation-candidate.sql` in the task workspace; it is not a release migration and no scheduler application code consumes it. Its system-only outbox records only an opaque routine ID, generation, timing and operation, avoiding retained space/user identifiers in deletion tombstones. With the gate off, its trigger does not change the generation or write an outbox row and does not access Graphile. The fixture applied 202 prior migrations with the separate setup-plan draft and unrelated notification migration excluded. On the real migrated `routines` table, tests covered gate-off reads and writes, an explicitly enabled version fence, same-time pause/rearm, transactional rollback, system-only RLS, deletion and reinsert generations, bot-cascade deletion, and two concurrent writers. A Prisma client regenerated from the deployed base schema `a5cdbe430` also exercised reads and updates against the candidate with the gate off and observed the fence with it on. These are isolated PostgreSQL 16 tests using synthetic data; they do not execute the old app image, the full migration CLI or any queue worker. The gate was restored off in the fixture.

Do not promote the candidate into release migrations until the old executable and supported deployment configurations have been checked, and until the previously listed queue, early-watch, cleanup, memory-driver, drain, privacy-retention and rollback contracts have a complete design and real tests. An old-schema generated client is useful compatibility evidence but is not proof that the old app binary and all of its concurrent schedule writers are compatible. Avoid enabling the candidate's gate until all participants honor a tested cutover protocol.

A real isolated Graphile/PostgreSQL interleaving showed that a new-version worker can admit a legacy v1 wake while the gate is off, then continue its watch handler after the gate is enabled. Checking the gate before dispatch is not a cutover barrier. Before enabling v2, stop v1 intake and drain every in-flight v1 handler, including handlers in new binaries, then handle queued legacy jobs. Do not infer that a database fence cancels already admitted work. The fixture used a simulated watch effect; no real watch or production job was run.

### Proposed rollback and deletion retention protocol

Status: proposal only. The system-only inventory reports capped aggregate counts, uses a read-only snapshot and a three-second statement timeout, and never returns routine IDs. It does not authorize a cutover, rollback, or cleanup: queue counts are point-in-time samples, not proof that workers or publishers have stopped. The inventory is not connected to an owner API, deployment, or cleanup. Missing Graphile access fails the inventory rather than reporting an empty queue.

A future rollback must first stop routine admission and all schedule producers, reconcilers and publishers, including older binaries, then prove that admitted v1 and v2 handlers and any uncertain effects have drained or been resolved. While the v2 gate remains on and that barrier is held, process pending deletion intents, reconcile orphaned upserts, and account for every v2 job, including locked or exhausted jobs with no key. Graphile's removal of a locked job clears its key and exhausts its retries but can leave its payload until the worker finishes. A safe implementation must wait for the relevant job rows and workers to disappear, then rebuild the legacy queue from a consistent active-routine snapshot under the same admission barrier before changing the gate. The existing code does not implement or prove this barrier, transactional rollback, reconstruction, memory-driver behavior, or old-image compatibility; merely setting the gate off can leave a v2 job and active outbox intent behind.

For privacy without resetting the reuse fence, investigate a new random lifecycle token per routine incarnation, carried in a new-version wake task and atomically checked with its generation on claim. Existing v2 tasks and workers do not enforce such a token, so a distinct task protocol and verified retirement of older workers are required. Once those workers and prior-lifecycle jobs are demonstrably drained, a bounded cleanup could lock an acknowledged delete tombstone, verify the routine is absent and the deletion generation unchanged, and remove it; a future recreation with the same ID must receive a fresh token. This is not safe with today's v2 protocol: deleting its tombstone can let a reused ID return to an old generation. Until the token, admission barrier, locked-job handling, retention policy and deletion/rollback failure tests exist, retain tombstones and treat their routine IDs and locked job payloads as deletion-privacy residue.

Synthetic PostgreSQL/Graphile tests exercised marked bot and space cascades, deletion intent publication, locked and unlocked job removal behavior, and the retained generation on ID reuse. A separate test rolled back its whole transaction after demonstrating that switching the gate off before deletion leaves a v2 intent and job. These tests do not exercise a real fleet drain, an old application image, account teardown end to end, or production data.

A uniquely named synthetic task in the existing isolated Graphile 0.17.3 fixture held a handler while its own runner was stopped. The stop waited for that handler, but the failed job was still locked immediately after both `runner.stop()` and `runner.promise` resolved; a later bounded observation found it unlocked and retained as exhausted. No live worker, port or container was changed. Cutover must therefore verify durable lock settlement after stopping workers, not infer it from process stop alone. The system-only `checkRoutineJobLockSettlement` operation uses separate bounded existence checks for locked v1 and v2 jobs, so a mixed capped sample cannot hide a lock. It reports only the observation and explicitly leaves admission stoppage and fleet drain unverified. Even a lock-free snapshot cannot rule out a new claim without a separately established fleet-wide admission barrier.

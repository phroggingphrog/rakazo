## Vertical-slice implementation constraints

1. The conversational assistant proposes a typed plan from an owner request and discovered capabilities. Persist the proposal and its lifecycle in the existing database, scoped to the actor; it is a draft and reference to real configuration, not another scheduler or a copy of live bot settings. The UI reads the same state on web and mobile.
2. Review must identify the selected existing connection, the exact read operation and known scope, schedule, bot and notification behavior. Unknown account or OAuth scope stays unknown; no password or token is collected in chat. A user-authorized transition applies only the reviewed plan using the existing bot, assignment and inactive routine paths, with an idempotency key and concurrency protection.
3. Record the actual test run ID and a snapshot of the routine, source revision and authorization relevant to that test. The server evaluates its terminal result and source-bound successful-read evidence; queued, failed, cancelled, missing, stale or changed configuration cannot become verified. A successful generic read alone does not establish account identity or source coverage.
4. Activation must recheck those facts at the write boundary and enable the same persisted routine the worker uses. Configuration edits or credential/assignment changes invalidate the old verification. Show proposed, awaiting approval, configuring, verified, active and failed based on persisted evidence and current state, including a truthful failure or intervention path.
5. Reuse existing integration settings, bot settings, routine editor, run history and notification surfaces. Unsupported scope introspection, non-MCP sources, write permissions, durable delegation and system actions remain explicitly unavailable until their real backends are verified. Add behavior-level component, API, concurrency and end-to-end tests; owner-facing and mobile checks remain release gates.
